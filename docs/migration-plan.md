# 移行計画

[ADR-0001](./adr/0001-azure-native-agent-architecture.md) で定義した最終形へ移行するための、フェーズ分割と各フェーズの完了条件を定める。

## 前提

- **既存サービスは停止している。** App Service 上のアプリはデプロイできておらず稼働していないため、無停止移行・後方互換・段階的リリースは考慮しない。壊してよい。
- **手順は書かない。** 各フェーズは「何が達成されていれば次に進めるか」だけを定義する。実装の分割、ファイル構成、命名、テストの粒度は実装時に判断する。
- **各フェーズの終わりで必ず動かして確認する。** ローカルで動くことではなく、デプロイして叩けることを完了の条件とする。

## フェーズ

### Phase 0: データの退避

Google Drive 上の日記とプロフィールを Cosmos DB へ全件移行する。

現在の同期は Functions のタイマーによる直近数日分の差分取り込みであり、**Cosmos DB が日記の全件を保持している保証がない**。かつ Phase 1 で Drive 連携コードを削除すると取り出す手段が失われるため、**この作業を最初に行う**。使い捨てのスクリプトでよく、リポジトリに残す必要はない。

- 完了条件: Drive 上の日記ファイル数と Cosmos DB の日記件数が一致している。プロフィールが Cosmos DB から読める。

### Phase 1: 更地にする

最終形で不要になるものをすべて削除し、新しいリポジトリ構成の骨格を作る。

削除対象は ADR-0001 の「廃止するもの」の表に従う（App Service と Bicep 定義、Google Drive / OAuth 一式、音声処理、`diary_workflow`、チェックポインター、LangSmith、docker-compose の postgres）。

- 完了条件: 不要な依存が `pyproject.toml` から消え、残ったコードで `ruff` とテストが通る。この時点でアプリは動かなくてよい。

### Phase 2: 基盤インフラ

Bicep で土台を用意する。Foundry アカウントとプロジェクト、既定モデルのデプロイ、Storage（Queue / Blob）、Application Insights、Key Vault、および Cosmos DB への RBAC 付与。Cosmos DB は既存のものを流用する。

- 完了条件: `azd provision` が通り、Foundry のプレイグラウンドから既定モデルに応答させられる。

### Phase 3: エージェント本体

Microsoft Agent Framework でエージェントを実装し、Responses プロトコルでホステッドエージェントとしてデプロイする。**ここではツールを最小限にし、まず経路を通すことを優先する。**

このフェーズが技術的な未知が最も多い箇所であるため、日記機能の実装より先に、デプロイして応答が返る状態を作る。

- 完了条件: エージェントのエンドポイントに直接リクエストして応答が返る。conversation ID を渡して会話が継続する。Application Insights にトレースが出ている。

### Phase 4: LINE 経路

Gateway（webhook 受信とキュー投入）と Worker（エージェント呼び出しと返信）を Functions で実装する。conversation ID は Cosmos DB の `users` に保持し、「閑話休題」で切り替える。

- 完了条件: 実機の LINE から話しかけて返事が返る。アイドル後の初回メッセージ（コールドスタート）でも返信が届く。

**ここでアプリが動く状態に戻る。** 以降は機能を戻していく作業になる。

### Phase 5: 日記機能

日記の CRUD ツール群、ベクトル検索、スキル、プロフィール参照を実装する。

- 完了条件: LINE 上で「今から昨日の日記を書く」と伝えてから本文を送ると日記が登録される。過去の日記の検索・修正・削除が会話から行える。

### Phase 6: 周辺機能

以下は互いに独立しており、並行して進められる。

- **バックアップ**: Timer Function で日記を Markdown として Blob Storage へ日次エクスポートする。
- **評価**: Foundry Evaluations の最小セット（想定発話10件程度）を用意し、ツール呼び出しの正確さとキャラクター応答を採点する。既定モデルと代替候補を同じセットで比較し、モデル選定の判断材料にする。
- **日記 Web UI**: ACA Express 上に閲覧・リネーム・削除ができる管理画面を用意する。

## 進め方

- **直列が必要なのは Phase 0 から 4 まで。** 依存関係があるため順に進める。Phase 5 以降は分割・並行して進められる。
- **各フェーズには完了条件だけを渡し、実装方法は委ねる。** 細かい手順を先に決めると、実装時に判明する制約と噛み合わなくなる。
- **フェーズをまたぐ前にデプロイして動作を確認する。** 特に Phase 3 と 4 は未知が多く、机上で正しくても動かない可能性がある。

## この計画で決めないこと

以下は実装時に判断する。

- ディレクトリ構成とモジュール分割の詳細
- ツールのシグネチャと粒度、スキルの記述内容
- システムプロンプトの文面
- テストの対象と粒度（CLAUDE.md の方針に従い、必要最小限とする）
- Bicep のモジュール分割
